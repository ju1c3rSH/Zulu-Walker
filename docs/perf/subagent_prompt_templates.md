# 子智能体提示词模板库

> 用途：把这些模板复制给任意 Agent，让它以同样的方式派发子智能体完成工作。
> 每个模板都标了**适用场景**、**填写槽位**、**验收标准**。
> 模板中的 `{...}` 是需要替换的槽位。

---

## 模板 A：只读调研（Explore 类子智能体）

**适用**：盘点现状、核对差异、找风险点。不改任何文件。

```markdown
你在 {仓库路径} 里做**只读调研**（用 git / grep / read，不要修改任何文件，也不要执行 git 写操作）。

## 背景
{一段话说明这个仓库/项目是什么，以及本次调研要解决什么问题}

## 调研范围（严格限定）
{明确到目录或文件级别，并给出对比基线}
- 基线：`{分支或 commit}`
- 目标：`{分支或 commit}`

用 `{git diff 基线..目标 -- 路径}` 看全量改动，并配合 `{git log --oneline 基线..目标}` 理解每个改动的动机。
相关提交里值得注意的有：{列出 commit hash + 一句话主题}

## 我要你产出的东西
按**主题**（不是按文件/提交流水账）组织，每个主题给出：
1. 主题名
2. 解决了什么问题（动机，来自 commit message / 代码注释 / docs）
3. 怎么做的（关键机制，涉及哪个文件）
4. 证据：`文件路径:行号` + 关键 commit hash

建议的主题方向（自行判断实际有什么，可增补可合并）：
{列出你期望拆解的维度}

同时请指出：{哪些是通用能力，哪些是平台/场景专属的}

## 交付格式
Markdown，中文。要有结构、有密度，不要贴大段代码（最多贴 5 行关键片段）。目标 {字数} 字 + 证据列表。
最后单列一节「我判断不准/需要作者确认的点」。

只报告你在代码里**实际验证过**的内容，不要根据提交信息脑补。文件行号必须真实存在且能对应到你描述的机制。
```

**要点**
- 基线/目标用 commit hash 写死，别用分支名（分支会移动）。
- 强制要求"实际验证过"，避免子智能体按 commit message 脑补。
- 末尾强制列"拿不准的点"，主 Agent 才能做取舍。

## 模板 B：分片并行改造（Worker 类子智能体）

**适用**：范围明确、可以按目录切成互不重叠的多个分片并行做。

### B-0 先做标定样本（重要）

**先自己改 1 个最具代表性的文件**，把标准固化下来，再派发并行子智能体。
标定样本的作用是让所有子智能体照同一个模子改，避免风格分裂。

标定样本应满足：注释密度最高、且包含你**最想保留**的那类关键注释。

### B-1 并行派发的提示词

```markdown
你在 {仓库路径} 里做**{任务名}**（这是唯一的任务，允许改文件）。

## 背景
{项目是什么 + 为什么要做这件事 + 目标状态}

**分支状态**：当前在 `{分支名}`（HEAD `{commit}`）。{工作区现状描述，如"某某文件已被我改好，不要碰它"}
{如果多个子智能体并行，说明彼此的文件所有权边界}

## 标定样本（必读）
请先读 `{标定样本文件路径}` 看我改完的样子，这是**标准样板**，照它的密度和风格做。

## 判断原则
- **保留**：读者不看注释就会踩坑、且无法从代码本身推出的事实。例如：
  - {硬件/固件约束、协议约定、平台差异}
  - "改了会导致静默错误行为"的警告
  - 参数的单位、取值含义、边界
  - 一句话能说清的"为什么这样设计"
- **删掉**：
  - 调试过程流水账（"某日实测…""第一版…第二版…"）
  - 根因分析的完整推导过程（保留结论，别保留推理）
  - 大段实测数据罗列（保留最终结论数字，删掉对比过程）
  - 历史沿革叙述、版本变化回忆
  - 重复代码本身就能表达的内容
  - 情绪化/强调性修辞（"⚠⚠"、"这是**关键**"、"全部实测确认："这类）
  - 已写进 docs/ 的深度分析的重复内容
- **压缩**：一个 20 行注释块如果核心信息 2~3 行能说清，就压成 2~3 行，**不要整个删掉**。
- **格式**：保持原有的缩进层级和 `#` 风格；原本带 ⚠ 的严重警告可保留 ⚠ 标记，删掉周围强调修辞。

## 你的任务范围（只改这些，不要碰别的）
```
{逐行列出文件路径}
```
**不要碰**：{显式列出禁止触碰的目录/文件}

## 特别提示
{逐条列出该分片里"压缩但不要删光"的高价值注释，附文件:行号}

## 重要约束
1. **只改{目标元素}，绝对不要改动任何代码逻辑、字符串字面量、配置值**。
   {配置类文件特别说明：如"YAML 里的值本身一个都不能动，只删 `#` 后面的文字"}
2. **不要删除 docstring 的功能性说明**（参数含义、返回值说明可精简但不能删空到没意义）。
   {契约层特别说明：如"HAL interface/ 是公共契约层，这里只做轻度精简，不要大删"}
3. 保持 UTF-8 编码，写回时不要加 BOM（用 write 工具直接写内容）。
4. **保持行尾风格一致**（先检查原文件是 CRLF 还是 LF，改完保持一致）。
5. {该分片特有的约束，如"YAML 必须仍是合法 YAML"}

## 验证要求（必须做）
改完后运行：
```
{测试命令}
```
必须仍然全绿（基线是 {N} passed）。如果失败，**必须修到全绿**。

另外{补充校验，如 YAML 解析 / AST 对比}：
```
{校验命令}
```

## 交付格式
完成后用 Markdown 中文报告：
1. 每个文件的注释行数变化（删前 → 删后），总体减少百分比
2. 删除的都是哪几类内容（分类列举）
3. **保留下来的、你判断最有价值的那 10 条注释**（列出文件:行号 + 一句话摘要），我要检查有没有误删
4. 测试结果
5. 你拿不准是否该删的地方（留了什么、为什么留）

不要写代码到报告里。目标 {字数} 字以内 + 列表。
```

### B-2 并行时的文件所有权切分原则

| 原则 | 说明 |
|---|---|
| **目录级切分** | 每个子智能体独占一个目录树，不要交叉 |
| **配置单独切** | YAML/JSON 配置常被多个模块引用，单独给一个子智能体 |
| **标定样本先做** | 主 Agent 先改好样本，再派发，否则风格会分裂 |
| **显式写"不要碰"** | 每个子智能体都要列出禁碰清单，否则会越界 |
| **并发上限** | 按子智能体并发上限决定分片数，不要盲目开 4 个 |

## 模板 C：验证子智能体（Verifier 类子智能体）

**适用**：交付前独立复核，不改代码。

```markdown
你在 {仓库路径} 里做**独立验收**，不要修改任何项目文件。

## 验收对象
{改动范围：分支/commit 区间，或具体文件列表}

## 验收标准
{逐条列出可判定的标准，每条都要能用命令或读码验证}

## 必须实际执行的检查
```
{具体命令}
```

## 报告格式
Markdown，中文。逐条给出 **通过 / 不通过 / 无法验证**，并附实际输出证据。
发现问题按 **严重度** 排序，每条给出 文件:行号 和修复建议。
不要给"看起来没问题"这种结论 —— 没有证据的结论一律标为"无法验证"。
```

## 模板 D：分支合并前的影响面核对

**适用**：合并分支前，先摸清拓扑和风险。

```markdown
你在 {仓库路径} 里做**只读 git 拓扑与影响面核对**。

## 任务
### A. 拓扑
用 `git merge-base --is-ancestor` 双向确认 {分支A} 与 {分支B} 的包含关系。
用 `git merge-base` 找出分叉点，用 `git rev-list --count` 算领先/落后提交数。
判断合并是 fast-forward、还是需要三方合并。

### B. 改动清单
`git diff --stat {基线}..{目标}` 列出全部改动文件。
按主题归纳：哪些是新增能力、哪些是行为变更、哪些是配置变更。

### C. 风险清单
逐项核查（**都要给证据**，查不到就说查不到）：
1. 公共接口层（{接口目录}）有没有被写死某平台假设
2. 平台注入逻辑（{工厂文件}）如何切换，有没有硬编码分支
3. 协议层（{协议目录}）是否逐字节一致、有无平台条件分支
4. 合并后的**默认配置值**是什么，会不会导致某平台链路不通
5. 有没有**只在某平台存在**的外部依赖（模型文件路径、串口路径、固件模块名差异）
6. 打包清单（{打包文件}）有没有条目丢失

### D. 测试基线
运行 `{测试命令}`，报告通过/失败数量。

## 交付格式
Markdown，中文。区分「已验证」与「存疑」。每条结论附 `文件:行号` 或命令输出。
不要贴大段代码。
```

## 通用验收清单（所有改造类任务都套用）

改造类子智能体最容易出 5 类错，主 Agent 收尾时逐项查：

| # | 风险 | 检查方法 |
|---|---|---|
| 1 | **误删代码行** | AST 对比：把新旧 AST 的 docstring 置空后 `ast.dump` 应完全相同 |
| 2 | **docstring 结尾换行被吃掉** | `ast.parse` 全量过一遍（本项目就踩到过 `"""` 与下一行粘连） |
| 3 | **配置值被顺手改了** | YAML 解析后逐键比对 `git show HEAD:file` 的结果，必须完全相等 |
| 4 | **BOM 引入** | 写回后检查前 3 字节不是 `EF BB BF`；Python 3 允许 BOM，但会破坏某些工具链 |
| 5 | **行尾风格变了** | 逐文件比对原 CRLF/LF，改完保持一致 |

**AST 对比脚本要点**：遍历 AST，把所有 `Module/ClassDef/FunctionDef` 的首个 `Expr(Constant(str))` 置空，再 `ast.dump` 比对。
这样既允许 docstring 变化，又能抓出任何真实代码改动。

## 分工与协作的通用建议

1. **主 Agent 做决策，子智能体做执行**。标准由主 Agent 定（用标定样本固化），子智能体不自行发挥。
2. **并行写入必须文件所有权互斥**。目录级切分最稳。
3. **子智能体被中断是常态**。中断后工作区会留半成品 + 临时脚本，主 Agent 要：
   - 跑 AST/YAML 对比确认没有真代码改动
   - 清掉子智能体生成的临时脚本，并加进 `.gitignore`
4. **收尾永远自己复验**，不要只信子智能体的"已全绿"报告——它可能测的是自己改完的中间态。
5. **子智能体报告里的"我拿不准的点"是金矿**，那往往正是需要你拍板的地方。
