## 0. 先修正两个读数误区（否则方向会错）

### 误区一：日志里的「未归因 21ms」不是黑洞

日志原文：

```
[PERF] vision 24.5Hz loop=40.9ms body=39.4ms cpu=17.6ms gil_wait=21.8ms
       | read=6.2(cpu7.08) conv=6.6 task=25.9(cpu10.05) disp=0.1(cpu0.09) none=0
       | idle=1.5ms 自身cpu=0.37ms 未归因=0.6ms
```

四项相加 = 6.2 + 6.6 + 25.9 + 0.1 = **38.8ms**，而 `body = 39.4ms`。
`loop(40.9) - body(39.4) = 1.5ms = idle`。

**结论：四项之和已经覆盖了 body，没有 16ms 的未解释时间。** 日志里的 `未归因` 公式
`loop_ms - parts - (loop_ms - body_ms)` 把 idle 重复减了一次，是个显示口径瑕疵。

### 误区二：`read(cpu7.08)` 的 cpu 比墙上(6.2)还大 —— 这是对的

`read_cpu = _c1 - _c0`，而 `_c1` 取在 `read_raw()` **返回之后**。`image2cv` 转换发生在
`read_raw -> _ingest_raw` **内部**，所以：

- `read_cpu` = 取帧 + `image2cv` 的 CPU 合计
- `conv` 是 `_ingest_raw` 里单独 `_mark_stage("convert")` 的墙上时间，**不重复计 CPU**

所以 `自身cpu = 17.6 - (7.08 + 10.05 + 0.09) = 0.38ms`，与日志 `自身cpu=0.37ms` 吻合。
**框架编排开销接近 0 —— 瓶颈不在框架。**

> ⚠ **必须把「墙上」与「CPU」两个口径分开，别混为一谈**（2026-10-09 二次核正）：
>
> - **墙上：`read` 与 `conv` 是两段互不重叠的时间**，**可以相加**（6.2 + 6.6 = 12.8ms）。
>   证据：`maixcam1/camera.py:383-385` 的 `_mark_stage("read")` 只包 `_read_nonblocking`；
>   `:348-351` 的 `_mark_stage("convert")` 只包 `image2cv`。两段串行、不重叠。
>   旁证：日志 `read=6.2 < conv=6.6` —— 若 read 含 conv 则必有 `read >= conv`，矛盾。
>   源码自证：`vision_manager.py:246` 直接 `parts = read + convert + tasks + disp`，
>   **框架自己就是把四项相加的**。
> - **CPU：`read_cpu` 确实包含 `conv` 的 CPU**（因为 `_c1` 取在 `read_raw()` 返回之后）。
>   所以 `own_cpu` 公式只扣 `read_cpu`、不再单扣 conv —— `vision_manager.py:248`
>   原文即「conv 的 CPU 天然包含在 read_cpu 里，**不重复扣**」。
>
> **一句话**：墙上可加、CPU 不可加。**P0-B 的收益记账按墙上口径算 = 省 `conv ≈ 6.6ms`
> （其中 `image2cv` 台架实测 ≈ 4.73ms，差额是 `[::-1]` 视图开销）。**

## 1. 瓶颈的真相：不是算法慢，疑似「被抢 GIL」

把 `task=25.9ms` 拆开：

| 构成 | 耗时 | 性质 |
|---|---|---|
| `find_blobs`（C++，持 GIL） | ~8.0-8.9ms | **纯 CPU** |
| blob -> dict 转换（含 3 个形状 getter） | ~0.3ms | 纯 CPU |
| Python 编排（阈值检查/判据/拼 dict） | ~0.5ms | 纯 CPU |
| **CPU 小计** | **~10.05ms** | 与日志 `task(cpu10.05)` 吻合 |
| **墙上 - CPU = 等 GIL / 被抢占** | **~15.85ms** | **纯等待** |

**视觉线程 24.5Hz / loop=40.9ms，但真正在算的只有 17.6ms。剩下 21.8ms 全在等。**

> 证据强度：`find_blobs ≈ 8.9ms` 来自台架实测，**可靠**；
> 但「墙上多出的 15.85ms 全是等 GIL」是**推断** —— 也可能是内核调度抢占
> （已绑核，但 CAM1 是双核小算力）或内存带宽争用。**归因方向对，比例未证实。**

疑似抢 GIL 的两大来源（**均为推断，未逐项实测**）：

1. **`display.show()`** —— 单次墙上 ~23-35ms 而 CPU 仅 ~3.9ms，即**每次调用持 GIL 等硬件
   约 20-32ms**。当前 `display_show_interval_ms: 1000`（1Hz），**摊到每秒仍冻结 ~23ms**。
2. **mainloop 75Hz 空转** —— `MAIN_LOOP_DELAY=2ms`，每秒 500 次；每次
   `coordinator.loop()` + `DebugConsole.set x6` + `touch.read()` 硬件读。
   日志 `coord.44ms tick.14ms touch.23ms`，合计 **~0.81ms/tick x 75Hz ≈ 61ms/s**。

> 台架对照（**可靠**）：**串行 read + find_blobs 单跑 59.7Hz（16.7ms/帧）**；
> **带全部线程的真机 24.5Hz（40.9ms/帧）**。差额 24ms ≈ 就是并发开销。

### P0-A｜比赛模式彻底关显示（**收益为推算，风险确为零**）

**现状（已逐行核实）**：`project_config.yaml:13` `display_enabled: true`，
`:80` `competition_mode: true`。两者是**正交开关** —— `competition_mode` 只关 HUD 绘制
与 JPEG 推流（`vision_manager.set_render_enabled:317`），而 `_maybe_show()` 读的是
`MainUiShell._display_enabled`（`app/main.py:288,362`），当前仍为 **true**，
所以 `display.show()` **照常以 1Hz 调用**。

**动作**：把 `display_enabled: false`。

**为什么这是"官方指定动作"**：`project_config.yaml:11-12` 注释自证：
> `false` = 完全不向 LCD 输出, 这是**彻底消除**那 32ms 冻结的**唯一办法**;
> 提速优先/比赛时: 直接 `display_enabled: false`, **归零**。

**收益（⚠ 修正）**：初稿"+12~15%"是**推算**。诚实表述：
- **确定**：每秒减少**至少 23ms** 的 GIL 冻结（23.4ms 有台架实测）。
- **不确定**：这 23ms 能换回几帧，取决于视觉线程当时是否恰好被挡。
  **乐观 ~+3 帧/秒，保守 +0~1 帧/秒**。
- **验收**：只看 `gil_wait` 是否下降。**下降了才算数，帧率涨不涨次要。**

**代价**：屏幕黑屏。触摸急停仍可用（退出图标命中框按帧宽高算，与上屏无关）。
**额外价值**：即使换不来帧率，**减少 GIL 争用对"时延抖动"也是净收益** ——
打靶是闭环控制，抖动比均值更伤 PID。

### P0-B｜TARGET 模式跳过 `image2cv`（❌ **已被证伪，降级为 P2**）

> ⚠ **本节在 2026-10-09 自审中被推翻。** 初稿的"返回轻量占位帧"**根本行不通**。

**现状**：`_ingest_raw()` 每帧无条件做 `image2cv(raw, copy=True)` + `np_rgb[:, :, ::-1]`
（`maixcam1/camera.py:349-351`）。

**自审证伪（三条，均已读源码确认）**：

1. ❌ **不能用 `None` 占位**。`gks_task_processor.py:810` 是
   `if not lab or frame is None: return {"err_fixed": 0, "found": False}` ——
   **frame=None 直接退化成零值心跳，TARGET 完全不检测**（`:745` EXPLOSIVE 同款守卫）。
2. ❌ **不能用"轻量假 frame"**。`_process_target:814` 立刻做 `h, w = frame.shape[:2]`，
   假对象缺 `shape` 会抛异常，被 `Task.execute` 吞成 `success=False`，同样停检。
3. ⚠ **"显示路径不依赖 numpy" ✅ 成立，但"调参页不受影响" ❌ 不严谨**：
   `_update_display_frame:314` 取的是 `pipe.camera.last_raw`（maix Image），
   显示线程零拷贝上屏 —— **这半句对**。但调参页走的是 `MaixCam1Camera.read()`
   （`maixcam1/camera.py:321-334`），而 `read()` **内部同样调 `_ingest_raw`**
   —— 它**不是**独立路径，和主流水线**共用同一个 `image2cv`**。
   所以若按"当前模式"在 `_ingest_raw` 里跳转，**调参页会一起变黑**。
   正确做法：跳过条件必须显式排除"调参页活跃"（如 `paused` / 显式 `want_numpy` 标志），
   **不能依赖"路径独立"这个不成立的假设**。

**真正决定"能否跳过"的消费者清单（已逐一定位）**：

| 消费者 | 位置 | 是否真需要 numpy |
|---|---|---|
| TARGET（find_blobs C++，scale=1.0） | `_process_target:838` | **否**（只用 `frame.shape`） |
| EXPLOSIVE（find_blobs C++，scale=1.0） | `_process_explosive:751` | **否**（`_downscale` scale>=1.0 原样返回） |
| **RESCUE（YOLO）** | `ai.detect(frame, ...)` `:1088` | **是，硬需求** |
| cv2 回退路径 | `_scan_blobs_cv:559` | 是 |
| 降采样 `scan_scale<1` | `_downscale:706-708` | 是 |
| 调参页 | `MaixCam1Camera.read()` | 是（**共用 `_ingest_raw`，非独立路径**，需显式保护） |
| `draw_result`（cv2 调试） | `:1150` | 是（`draw_enabled` 默认 False） |

**修正后的动作（唯一可行形态）**：不是"返回 None"，而是**新增一条
"本帧 numpy 是否有效"的契约**：`_ingest_raw` 在"当前模式不需要像素"时跳过 `image2cv`，
但**仍返回 1x1x3 的 `np.zeros` 占位**（保住 `frame is not None` 与 `frame.shape` 两个不变量），
并置 `last_frame_is_placeholder=True`；RESCUE 与 cv2 回退路径在入口检查该标志。

**⚠ 风险从"低"上调为"中"**：
- 跨越 `camera.py` / `pipeline_camera.py` / `gks_task_processor.py` / `vision_manager.py`
  **四处**新增契约，任一处漏判 -> 人质任务静默失效或 cv2 回退档崩。
- ⚠ **调参页共用 `_ingest_raw`**（`read()` 内部也调它），跳过条件必须显式排除
  "调参页活跃"，否则调参页一起黑。
- `tests/test_gks_review_fixes.py:128` 锁定 `read_raw()->None` 语义，改动会牵动它。

**修正后结论**：**降级为 P2，理由是"风险"（跨 4 文件契约 + 调参页共用），
不是"收益小"。** 墙上收益仍是 **`conv ≈ 6.6ms`**（见 §0 二轮核正）。
用 4 个文件的契约复杂度换 6.6ms 值不值，取决于 P0-A / P1-A 之后还剩多少预算 ——
**先做那两项再看。**

### P1-A｜拉低主循环空转频率（收益为推算，建议先做）

**现状**：`framework/module_manager.py:16` `MAIN_LOOP_DELAY = 0.002`（声明 500Hz），
而视觉只有 24.5Hz。

> ⚠⚠ **关键发现（2026-10-09 核正）**：日志实测主循环 **只有 75Hz，不是 500Hz**。
> 若真按 2ms 睡眠，理论应是 `1/(0.98+2)ms ≈ 335Hz`。**75Hz 意味着每 tick 实际
> 睡了 >=13.3ms** —— `time.sleep(0.002)` 在 Linux 上受调度粒度限制，
> 或存在未计入的隐式等待。
> **这推翻了初稿「每秒抢 500 次 GIL」的推算。真实只有 75 次/秒。**
> 所以 P1-A 的收益**不能**按"减少 500->200 次抢锁"来算 ——
> **75Hz 本身已偏离 sleep 预期，改动后的实际行为必须实测，不能外推。**

**动作**：`MAIN_LOOP_DELAY` 提到 **0.005**（200Hz）。
（它是**类常量**。改法：实例化时从 `project_config.yaml` 读 `main_loop_delay_ms`，
**2ms 为默认** —— 与项目"配置缺键即保持改前行为"惯例一致，可一键回退。）

**为什么安全**：`_push_allowed():263` 新结果路径放行延迟 = **1 个 tick**。
即使按声明值 2ms->5ms，推流时延也只 +3ms；视觉帧周期 40.9ms，3ms 只占 7%。
**⚠ 但注意上面 75Hz 的发现**：实际 tick 间隔已是 ~13ms，改 sleep 值未必线性生效。

**收益（⚠ 修正，把握低）**：
- 初稿"省 ~40ms/s CPU / 少 300 次抢锁"**已作废**（基于错误的 500Hz 假设）。
- **真实现状**：75Hz × 0.98ms body = **~68ms/s 主循环 CPU**（日志直给，可靠）。
- 改后能否下降、降多少 —— **必须实测**，因为 75Hz 异常说明睡眠行为非线性。
- **验收**：`[PERF] mainloop` Hz 与 `每秒 CPU` 是否下降；`[UART TX] DATA_STREAM` Hz **不得下降**。

**⚠ 上限（关键）**：不能超过相机帧间隔的一半（60fps -> 16.7ms -> 上限 8ms）。
但 tick 拉太长会让"多个结果挤在一拍"概率上升，推流率反降。
**5ms 稳妥，8ms 必须实测后才敢用。**

### P1-B｜`track_roi_px` 从 64 收到 48（**结论：不要做**）

**收益表**（`find_blobs` 成本 ≈ 线性于像素数，锚点 640x197=8.96ms —— 台架实测，**可靠**）：

| `track_roi_px` | 窗口 | 扫描像素 | 单帧成本 | 相对全 ROI 省 |
|---|---|---|---|---|
| （关） | 640x197 | 126080 | 8.96ms | — |
| 96 | 192x197 | 37824 | 2.69ms | 6.27ms |
| **64（当前）** | **128x197** | **25216** | **1.79ms** | **7.17ms** |
| **48** | **96x197** | **18912** | **1.34ms** | **7.62ms** |
| 32 | 64x197 | 12608 | 0.90ms | 8.06ms |

**为什么不做**：64->48 只多省 **0.45ms**，而**一次 miss = 白花一次窄窗(1.34) +
一次全 ROI(8.96) = 10.3ms**。**miss 率只要上升 0.45/10.3 ≈ 4.4%，收益即归零。**
**结论：保持 64。** 自审后从"可选微调"直接定为"不要做"。

### P2-A｜动态跟踪窗（**已实现 2026-10-15**）

`target.track_mode: dynamic`：窗中心对齐上帧 (cx,cy)，
宽 = `min(2*track_roi_px, max(track_win_min_w, track_win_scale*blob_w))`，
高 = `min(roi高, blob_h + 2*track_v_pad_px)`。横宽纵窄贴合"云台只闭环 X 轴"；
双向封顶保证任何一帧的窗口不大于 fixed 窗（2*pad × roi高），miss 成本也不高于 fixed
（窄窗更小）。未命中仍当帧回退全 ROI，结果语义不变（测试钉住）。
配套 opt-in 候选填充率过滤（`target.fill_min/fill_max`，环≈0.5~0.7 vs 实心矩形≈0.9+；
cv2 路径内孔被填实（环≈0.79），max 须留余量并真机标定，默认全开区间=关；
空集回退不过滤，不制造漏检）。
HUD 青框显示当前窗；命中日志含平均窗面积与累计扫描次数。
回退：`track_mode: fixed`（原行为）/ `off`（关闭）。

`find_blobs_maix` 对每个 blob 读 `roundness/density/solidity` 塞进 dict

## 4. 修正后的执行顺序与预期总账

| 步骤 | 动作 | 预期 | 收益把握 | 风险 |
|---|---|---|---|---|
| **1** | **P0-A 关显示** | 40.9ms -> 38.5ms? | **中等**（GIL 冻结↓ 确定，帧率↑ 不确定） | **零** |
| **2** | **P1-A 主循环 2->5ms** | ->36.5ms? | 中等（CPU↓ 确定） | **低** |
| **3** | P2-B 瘦身包装 | ->36.4ms | 低（~0.1ms） | 极低 |
| 4 | P2-A 自适应窗 | ->33ms? | **低**（假设为主） | 中 |
| 5 | P0-B 跳 image2cv（重新设计后） | ->29ms? | 中（**墙上 6.6ms** 可信） | **中** |

**⚠ 与初稿的最大差别**：**P0-B 从第 2 位降到第 5 位**。它需重新设计跨 4 文件的契约
（且 `_ingest_raw` 被调参页共用）。**降级理由是"风险"，不是"收益小"** ——
墙上收益仍是 6.6ms。**先把零风险的 P0-A 和低风险的 P1-A 做掉**，
用实测判断还剩多少空间，再决定是否动 P0-B。

**关于总目标的诚实表述**：初稿"24.5Hz -> 33Hz"是**五个推测收益的简单叠加** ——
它们都指向同一段 GIL 等待时间，**不可能各拿各的份**。
**实际可期区间 24.5 -> 28~32Hz**，而非确定的 33Hz。

**最重要的观念修正**：
> 打靶是**云台闭环**，控制量是误差。**时延的"抖动"比"均值"更伤 PID**。
> P0-A/P1-A 的真正价值不只是"更快"，而是"**GIL 争用减少 -> 时延更可预测**"。
> 即使帧率没涨，闭环性能仍可能改善 —— **验收要同时看时延方差，不能只看均值。**

## 6. 一句话总结

> 当前 TARGET 帧率 24.5Hz **不是算法慢** —— 识别链路隔离跑能到 **59.7Hz**（实测）。
> 疑似的元凶是 **GIL 竞争**：`display.show()` 每次冻结 ~23ms 的锁、
> 主循环 75Hz 每秒抢 75 次 GIL（**归因方向可信，比例未证实**）。
>
> **自审后修正的可执行建议**：
> 1. **先做 P0-A（关显示）** —— 零风险，且它本身就是"验证 GIL 假设"的实验。
> 2. **再做 P1-A（主循环降频）** —— 低风险，保留一键回退。
> 3. **P0-B 降级** —— 墙上收益仍有 6.6ms，但代价是跨 4 文件契约 + 调参页共用路径，**风险不值得冒进**。
> 4. **明确不做** P1-B（数学上不划算）、P1-C（赛前风险太高）。
> 5. **别指望"叠加到 33Hz"** —— 各方案抢的是同一段时间，现实区间 **28~32Hz**。
